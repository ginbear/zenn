## はじめに

この 1 年弱で、EKS のバージョンを複数世代にわたってアップグレードしました。複数環境があるので、合計で 20 回近いクラスタアップグレードを実施したことになります。

この記事では K8s アップグレードの具体的な手順ではなく、AI と一緒に運用手順書を育てるプロセスについて書きます。

## 背景

### K8s アップグレードは環境依存が大きい

Kubernetes のアップグレードについて、公式ドキュメントには方針レベルのガイドがあります。

- K8s 公式: [Safely Drain a Node](https://kubernetes.io/docs/tasks/administer-cluster/safely-drain-node/)、[Upgrade A Cluster](https://kubernetes.io/docs/tasks/administer-cluster/cluster-upgrade/)
- AWS EKS: [Best Practices for Cluster Upgrades](https://docs.aws.amazon.com/eks/latest/best-practices/cluster-upgrades.html)

「cordon → drain → ノード入れ替え」「PDB を設定しましょう」といった原則は書かれていますが、実際のオペレーション手順は各組織の環境に合わせて自分たちで組み立てる必要があります。Terraform でノードを管理しているのか、ArgoCD でデプロイしているのか、Node のオートスケーラーをどう扱うか。組み合わせで手順は大きく変わります。

### 手順書はあるが、実作業で課題が見つかる

私たちのチームにも手順書はありました。しかし実際に作業をすると、曖昧な記述、確認漏れ、環境差異による想定外の挙動に遭遇します。手順書に書かれていない部分は、作業者の経験やコンテキストでカバーしていました。それは暗黙知であり、人が変われば同じ作業品質を維持できる保証はありません。

そして作業中に手順書を直す余裕はありません。作業が終わった頃には「あそこ分かりにくかったな」という記憶も薄れています。

## やったこと: AI と一緒にふりかえる

アップグレード作業を Claude Code と一緒に実施し、作業完了後にそのまま手順書のふりかえりと改善を行うようにしました。

### サイクル

```
1. Claude Code に手順書を読ませて作業を実行
2. 作業中に気づいた問題や改善点を issue にメモ
3. 作業完了後、同じセッションで手順書を改善する PR を作成
```

ポイントは「同じセッション」で行うことです。作業中のコンテキストがそのまま残っているので、何が問題だったか、なぜその手順が必要かを Claude Code が理解した状態でふりかえりに入れます。

## 具体例

約 20 回のイテレーションの中から、手順書がどう変わったかの例をいくつか紹介します。

### 1. AI に任せる範囲を広げる

最初は PR 作成や issue への記録など無難な作業から任せ始めました。回を重ねるうちに、手順書の中で役割分担を明確にし、AI に任せる範囲を徐々に広げていきました。

| 担当 | やること |
|------|---------|
| 人間 | apply の承認、異常時の判断、ArgoCD の目視確認、作業の進行指示 |
| Claude Code | コマンド実行、結果の記録、手順書の読み取り、PR/issue の作成 |

全自動にはしていません。人間が判断し、何かあった時にハンドリングできる状態を維持しています。

AI も手順を飛ばしたり、間違ったリソース名でコマンドを実行することがあります。実際にアップグレード中にそういうケースがありました。そのため、人間が全手順の実行を見ており、terraform apply などの破壊的操作は人間の承認なしに実行しない運用にしています。加えて、Claude Code の [hooks](https://docs.anthropic.com/en/docs/claude-code/hooks) で機密ファイルの誤コミットをブロックしたり、手順書側に確認コマンドを組み込んでミスを検出できるようにするなど、AI が間違える前提でのセーフティネットも整備しています。

### 2. 確認手順のコマンド化

初期の手順書には「AWS コンソールで Node Group が作成されたことを確認」のような記述がありました。人間が Web UI を見て確認する前提です。

これを CLI コマンドに置き換えていきました。

```bash
# 新しい Node が Ready になったか確認
kubectl get nodes -l eks.amazonaws.com/nodegroup=${NEW_NODE_GROUP}

# クラスタバージョンが期待通りか確認
aws eks describe-cluster --name ${CLUSTER_NAME} \
  --query 'cluster.{version:version,status:status}' --output table
```

コマンドにすると AI が実行できるので、再現可能で漏れがない。結果は issue に自動記録され、人間は出力を見て判断するだけになります。

AWS や K8s のベストプラクティスで推奨される確認項目（サブネットの空き IP、IAM ロールの存在確認、PDB の状態など）も、AI が実行するならコストが低いので積極的に手順に盛り込みました。手動では毎回実行するのが現実的ではない確認も、AI なら手軽に組み込めます。

### 3. 増やすだけでなく削る

手順書は放っておくと肥大化します。確認項目を増やすのは大事ですが、冗長な手順は作業時間を浪費し、重要な手順を見落とす原因にもなります。

毎回のふりかえりで「この手順は本当に必要か？」を AI と一緒にレビューしました。すぐ古くなる情報は公式へのリンクに置き換え、AI が生成できるものは手順書から外し、動かないコマンドの回避策を併記するのをやめて動く方だけ残す、といった整理です。

ある回では新規追加 25 行に対して 50 行削減し、改善しながら手順書を短くできました。

### 4. 手順書を AI 自身にレビューさせる

手順書の読者は人間だけではありません。Claude Code が読んで実行するので、AI にとって曖昧でないことが重要です。

改善した PR を AI 自身にレビューさせ、冗長・矛盾・解釈が分かれそうな箇所をチェックしました。実際にこのレビューで「同じ確認ルールが 2 箇所に書かれていて内容が微妙に違う」という矛盾が見つかり、修正しています。

AI が正確に実行できる手順書は、人間が読んでも分かりやすい手順書です。この方向で磨き込むと、結果的に手順書全体の品質が上がっていきました。

## 改善の実例: drain の安全性を上げる

ここまで手順書の育て方について書きました。ここからは、実際に手順書がどう変わったかの具体例を 1 つ紹介します。

K8s アップグレードでは、旧ノードから新ノードへ Pod を移動させるために [Node の drain](https://docs.aws.amazon.com/eks/latest/userguide/migrate-stack.html) を行います。この作業が最も時間がかかり、サービス影響のリスクがある部分です。ノードを 1 台ずつ drain していくのですが、前のノードの drain で移動した Pod がまだ起動中のまま次のノードを drain すると、同じ Deployment の Pod が同時に落ちる可能性があります。

以前の手順書では「1 台 drain したら ArgoCD の画面を見て、Pod が回復したら次に進む」という運用でした。これだと目視確認に頼ることになり、ノード数が多いと時間もかかります。

ふりかえりの中で Claude Code と議論し、2 つのコマンドを手順に追加しました。

1 つ目は drain の順序決定です。Pod 数が多いノードから先に drain することで、大量の Pod が早い段階で新ノードに移動を始め、後続のノードを drain している間に回復が並行して進みます。安全チェックで待つ場面でも、先に多くの Pod が回復済みなので待ち時間が短くなりやすいという狙いです。

```bash
# Pod 数が多い順にノードを表示
kubectl get pods -A --field-selector status.phase=Running \
  -o custom-columns=NODE:.spec.nodeName --no-headers \
  | grep -Fxf <(kubectl get nodes \
    -l eks.amazonaws.com/nodegroup=${CURRENT_NODE_GROUP} \
    --no-headers -o custom-columns=':metadata.name') \
  | sort | uniq -c | sort -rn
```

2 つ目は、次のノードに進む前の安全チェックです。Not-Ready な Deployment の Pod が次の drain 対象ノードにいないかを確認します。

```bash
# Not-Ready Deployment を取得し、次のノードに該当する Pod がいるか確認
NOT_READY=$(kubectl get deploy -A --no-headers \
  | awk -F'[ /]+' '$3 != $4 {print $1, $2}')
echo "Not-Ready Deployments: $(echo "$NOT_READY" | grep -c . || true)"
# ... 次のノード名で grep して該当があれば待つ
```

直近のアップグレードで初めて使いました。実際に Not-Ready な Deployment の Pod が次の drain 対象ノードにいるケースを検出し、別のノードを先に drain することでサービス影響を回避できました。まだ実績は 1 回なので引き続き検証中ですが、方向性としては手応えがあります。

## 結果

| | 初回 | 直近 |
|---|---|---|
| 作業時間 | 約 3 時間 | 約半分に短縮 |
| 確認項目 | 基本的な確認のみ | AWS ベストプラクティスの推奨項目も網羅 |
| 作業ログ | 作業後にまとめて記録 | リアルタイムで issue に整理して記録 |

作業時間の短縮には、作業者自身の慣れも大きいです。初回は不慣れな中での作業だったこともあり時間がかかっていました。ただ、慣れだけでは確認項目を増やしながら時間を短縮するのは難しいと思います。AI にコマンド実行や記録を任せたことで、人間の作業量を増やさずに手順の密度を上げられたのが効いています。

他に変わったこと:

- コマンド実行や PR 作成は AI に任せ、人間は「この差分で apply していいか」「この Pod の状態は問題ないか」の判断に集中できるようになった
- 手順書が毎回更新されるので、次の作業者（または AI）が最新の知見で作業できる
- 本番アップグレードに対する精神的な負担が減った。手順書とチェックコマンドが整備されていることで、「何か見落としていないか」という不安が小さくなった

## おまけ: ハーネスエンジニアリングとの接点

この記事を書いている最中に、[ハーネスエンジニアリングとは](https://speakerdeck.com/kinopeee/hanesuenziniaringutoha) という資料を読みました。AI エージェントの振る舞いを制御する「モデル以外の層」をハーネスと呼び、その設計・運用を体系化する考え方です。

資料では複数の流派が紹介されていますが、この記事でやったことは Hashimoto 派（HashiCorp 創業者）の考え方にほぼそのまま当てはまります。エージェントが失敗したら環境（手順書）を再設計する。設計物ではなく育てていくものとしてハーネスを捉える。名前を知らずにやっていたことに、後から名前がついた形です。

一方で、他の流派の視点を取り入れる余地もあります。

- **事後検証の自動化**: 現在の手順書には事前チェックや各ステップの確認コマンドはあるが、作業中にメトリクスを継続監視する仕組みはない。作業中のエラーレートや latency を自動で監視し、閾値を超えたら警告する sensors を組み込めると、異常の検知が早くなる
- **環境固有の知見の分離**: 手順書に環境固有の注意点を書くと肥大化する。手順書はジェネリックに保ち、環境ごとの知見は別のレイヤー（AI のメモリや環境別の補足ドキュメント）で補完する構造にすると、手順書の見通しを保てる
- **中断・再開の明示的なサポート**: 作業が中断した場合に、次のセッションで途中から安全に再開できるチェックポイントの仕組み

手順書を育てるサイクルは回せるようになったので、次はハーネスの構造自体を見直すフェーズに入れそうです。

## おわりに

手順書の改善は地味な作業ですが、AI と一緒にやることで「作業→ふりかえり→改善」のサイクルを低コストで回せるようになりました。

AI が読んで実行できるレベルまで手順書を整備すると、それは人間にとっても安全で再現可能なオペレーションになります。K8s アップグレードに限らず、運用手順書を持つチームであれば同じアプローチが使えると思います。
